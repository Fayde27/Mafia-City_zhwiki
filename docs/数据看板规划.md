## 三、關鍵架構決策

### 3-0 ⚠️ 口徑鐵律：看板只認真實值

`Article.views` 是**注水數**（每次隨機 +1~5），只給前台展示用。

> **看板的任何數字都不得取自 `views`。**
> 看板數據源只有兩個：`DailyStat` / `SearchLog`（新建）與 `Article.realViews`。

否則各模塊口徑不一致、且所有數字都是假的。

### 3-1 現有「在表上加計數列」的做法做不了日/週/月

計數列只存一個數字，沒有時間資訊。要按日週月，**必須換成按天聚合表**。

### 3-2 地基：一張按天聚合表

```
DailyStat(date, metric, key, count)

2026-09-10 | page   | /wiki/lineups | 120
2026-09-10 | item   | item_abc      |  30
2026-09-10 | lineup | lineup_xyz    |  45
2026-09-10 | search | (總次數)       | 203
```

- 一張表覆蓋**全部**維度，不必給每個模塊加列
- 日/週/月 = 「加總某段日期」，隨意切
- 行數可控：每天約數百行，一年數萬行
- 累計總數 = 全部相加；`Article.realViews` 可保留作快速讀取
- 寫入需 Postgres 函數做 upsert 原子遞增（參考已有的 `increment_article_views` 寫法）

### 3-3 搜索詞另開一張

```
SearchLog(date, keyword, count, hasResult)
```

`hasResult` 建表時就是多一個布林列，成本近乎為零，卻能產出「**搜了但沒結果**」清單 —— 全看板唯一能直接驅動行動的產出（等於選題表）。**因此列入一期。**

### 3-4 埋點統一走新 API `/api/track`，不擴充 `/api/wiki/view`

- 新開 `POST /api/track`，統一收 `{ metric, key }` 寫入 `DailyStat`
- 舊的 `/api/wiki/view` **保持原樣不動**（它還背著前台注水展示數的邏輯）
- 兩件事職責不同，混在一個 route 裡以後很難拆

### 3-5 不引入圖表庫

專案目前無圖表庫。`recharts` 之類會明顯增加打包體積（Cloudflare Pages 有體積考量）。
**條形圖用 CSS、折線用手寫 SVG**，零依賴。

### 3-6 不做防刷（已拍板）

維持現狀：刷新一次即計一次。

⚠️ **已知影響**：絕對值會偏高，自行測試時反覆刷新也會計入。
**看板使用原則：看趨勢與相對比較，絕對值心裡打折。**

### 3-7 數據保留 1 年（已拍板）

- `DailyStat` / `SearchLog` 只保留近 **365 天**
- 清理方式：Cloudflare Pages 無 cron，在 `/api/admin/analytics` 被訪問時順手 `DELETE WHERE date < now() - 365d`（低頻、成本可忽略）

## 五、各需求的可行性與口徑

| 需求 | 難度 | 說明 |
|---|---|---|
| 整站 PV | 低 | DailyStat 的 `page` metric |
| 模塊點擊 | 低 | 各模塊是不同 URL：`/wiki/lineups`、`/wiki/guides`、`/wiki/items`、`/wiki/events` |
| 文章點擊 | ✅ 已做 | 接入 DailyStat 後可再獲得日/週/月趨勢（用 `realViews`，不用 `views`） |
| 道具點擊 | 低 | 有獨立詳情頁 `/wiki/items/[slug]`；注意須繞開 2-1 的早退 |
| 搜索量＋熱搜詞＋無結果詞 | 中 | 需 SearchLog；注意空搜索去重、關鍵字長度截斷 |
| **流派點擊** | ⛔ **一期不做** | 見 5-1 |

### 5-1 ⛔ 流派點擊：一期不做（已拍板）

流派是 `/wiki/lineups` **頁內的篩選按鈕，不換 URL**。原本考慮的兩個方案都不成立：

- **A：統計篩選按鈕點擊次數** —— 便宜，但語義是「多少人主動篩選過這個流派」，**不等於流派受歡迎程度**。掛上看板一定會被當成後者讀，花成本做一個會誤導決策的數字，不如不做。
- **B：統計陣容卡曝光（可視區偵測）** —— 貴一檔，且預設全展示的情況下，曝光量基本等於列表順序，同樣不準。

**二期若要做，用替代口徑：**
> 按流派統計「其下各陣容詳情的點擊」——陣容本身有 `genreId`，直接從 DailyStat 的 `lineup` 維度反查聚合即可。**零額外埋點，語義真實。**

### 5-2 關於 Cloudflare Web Analytics

Cloudflare Pages 免費自帶整站 PV／各 URL 訪問量／來源／裝置，不用寫碼、bot 過濾更準。
**但它的數據在 Cloudflare 後台，無法方便拉進自建看板**（需 GraphQL API + Token）。
既然要「一個頁面看完」，**看板數字全部自建**，Cloudflare Analytics 留作交叉核對（判斷自建數字有沒有被 bot 灌水 —— 因為不做防刷，這個核對更重要了）。

### 為什麼聚合放 DB 側（別改回來）
PostgREST 預設單次最多回 1000 列。一年的 DailyStat 有數萬列，
撈回前端聚合會被**靜默截斷**、數字直接是錯的且不會報錯。
所以所有 group by / sum 一律寫成 SQL 函數。

  目前無呼叫點。二期若要做流派數據（5-1 替代口徑），前提是先有陣容詳情頁或可點卡片。
